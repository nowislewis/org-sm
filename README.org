#+title: org-sm
#+author: Lewis Liu

Minimal incremental reading for org-mode, inspired by SuperMemo.

*Design rule: capture is dumb, review is smart.*  Capture only stores the raw
material — instant, no AI, no judgment.  Every AI action operates on an
*existing* card, once the material has proven worth the effort.

#+begin_example
  grab text ──► capture (verbatim) ──► review ──► refine / split (AI, optional)
                 M-z, C-c C-c                     C-c s A, C-c C-a
#+end_example

* Extension interfaces

=org-sm-card.el= is a read-only storage module independent of FSRS and review UI.
=org-sm-card-at-point= and =org-sm-cards-in-file= return the same metadata plist:
=:type= (symbol), =:id=, =:title=, =:dismissed=, =:interval-days=, =:reviews=,
=:child-topics= and =:child-clozes=. Descendant counts include all nested cards.
File scans use temporary Org buffers without user mode hooks and prefer unsaved
contents of an already visiting buffer. Historical postpone/explain log lines
are excluded from repetition counts without rewriting files.

Frontend operations use =org-sm-body-text= / =org-sm-body-bounds=,
=org-sm-set-body= / =org-sm-set-title=, =org-sm-extract=,
=org-sm-capture-card=, =org-sm-preview-cloze=, =org-sm-grade-cloze=,
=org-sm-topic-interval= / =org-sm-topic-afactor=, =org-sm-grade-topic=,
=org-sm-grade-postpone= and =org-sm-dismiss=. Mutation operations write to the
current buffer but do not save it automatically. These are not pure functions.

Review actions return an event with =:action=, pre-action =:card=, =:session=
and action-specific fields. Session membership matches the exact presented
card marker, not merely another heading in the same buffer. =:old-days= / =:new-days= are card intervals;
postpone duration is =:postpone-days=, not the new interval. UI formatting is
separate through =org-sm-banner-function=, =org-sm-feedback-function= and
=org-sm-finish-function=.

=org-sm-after-review-functions= receives action events;
=org-sm-after-card-change-functions= also receives creation, editing,
extraction and restoration events. Observers must not modify events. Errors in
observers are reported without failing an already completed write. Session
summaries should count only events with =:session=, excluding postponements.
These notifications cover package operations, not arbitrary manual Org edits.

* Card Types

*topic* — repeated reading passage.  No grading; interval grows by A-Factor.

| Priority      | A-Factor | Behavior                       |
|---------------+----------+--------------------------------|
| =[#A]=        |      1.2 | slow growth, review frequently |
| =[#B]=        |      1.5 | moderate                       |
| =[#C]= / none |      1.8 | fast growth, fades out quickly |

*cloze* — fill-in-the-blank with ~{{answer}}~ markers, scheduled by
[[https://github.com/bohonghuang/fsrs.el][FSRS]].  Answers are hidden as
~[___]~ during review; rated again / hard / good / easy.

* Installation

Requires Emacs 29.1+, org 9.6+, [[https://github.com/bohonghuang/fsrs.el][fsrs]].

#+begin_src elisp
(use-package org-sm
  :hook (org-mode . org-sm-mode)
  :config
  (setq org-sm-directory "~/notes/")   ; inbox: sm-cards.org, created on demand
  (global-org-sm-read-mode 1))         ; M-z captures from any buffer

(with-eval-after-load 'org-sm
  (define-key org-mode-map (kbd "C-c s m")   #'org-sm-item-mark)
  (define-key org-mode-map (kbd "C-c s x")   #'org-sm-item-extract)
  (define-key org-mode-map (kbd "C-c s r")   #'org-sm-review-start)
  (define-key org-mode-map (kbd "C-c s SPC") #'org-sm-review-confirm)
  (define-key org-mode-map (kbd "C-c s d")   #'org-sm-item-dismiss)
  (define-key org-mode-map (kbd "C-c s q")   #'org-sm-review-abort)
  (define-key org-mode-map (kbd "C-c s t")   #'org-sm-tree)
  (define-key org-mode-map (kbd "C-c s A")   #'org-sm-card-workbench)
  (define-key global-map   (kbd "C-c s c")   #'org-sm-capture)
  (repeat-mode 1))
#+end_src

* Review Flow

- *topic:* ~review-start~ → read → ~review-confirm~ (reschedules, next item).
  Press ~x~ instead of ~r~ to have the AI underline passages worth
  extracting in the text on screen (optional, needs ~org-sm-gptel~); it does
  not advance the queue.
- *cloze:* ~review-start~ (hidden) → ~review-confirm~ (reveals) →
  ~review-confirm~ (rate).

Every prompt also offers *skip* (no change; stays due) and *dismiss*.
With Emacs `repeat-mode' enabled, after starting a review you can repeatedly
press ~r~ to confirm, ~d~ to dismiss, ~p~ to cycle priority, or ~a~ to abort.
Intervals are computed from the scheduled date, so early/late reviews don't
distort spacing.

** What a session contains, and in what order (org-sm-queue)

One ordering serves every entry point; a light session is its first six
cards and a full session all of them, so Emacs and the phone cannot
disagree about what comes next.

- *Clozes lead.*  A late cloze loses recall along a forgetting curve; a late
  topic loses only the chance to read it.  Review clozes are served first,
  most at risk first, where risk is days past due over interval days -- the
  poor man's `1 - retrievability'.
- *New clozes queue behind review clozes.*  A card never reviewed has no
  memory to lose, so it belongs with new material rather than ahead of recall.
- *Topics fill `org-sm-review-topic-proportion' (0.34) of the slots*,
  longest waiting first.  A share rather than "after all clozes", or a recall
  backlog would stop new material from ever arriving; and capped rather than
  unlimited, or reading would starve recall.
- *Priority wins inside a lane.*  `[#A]`/`[#B]`/`[#C]` reorder cards of the
  same type; they never move a topic ahead of the cloze stream.

Nothing is written.  The due pool is derived on every call, so a card left
over simply takes part in the next ordering.  There is deliberately no
auto-postpone: SuperMemo needs one because its outstanding queue is stored
state, while here a nightly rewrite would only add diffs, sync conflicts and
a counter to tune.  Simulated on a 199-topic backlog, postponing got 81 cards
read in 180 days where plain oldest-first reading got through 505.

** Lifecycle: stalled topics and leeches

Two predicates in =org-sm-card.el= keep a card from quietly wasting slots:

- ~org-sm-stalled-p~: a topic repassed ~org-sm-stall-review-threshold~ (4)
  times with no children.  Four passes without an extract or a dismissal is
  avoidance, not reading; the review prompt says so and offers the keys that
  actually resolve it (suggest, workbench, dismiss).
- ~org-sm-leech-p~: a cloze rated ~again~ ~org-sm-leech-again-threshold~ (2)
  times.  One lapse is noise; two means the card tests something never encoded,
  so the prompt offers a rewrite instead of another rating round.

** Neural review (org-sm-neural)

~org-sm-neural-start~ (~N~ in the review and tree maps) ignores dates and walks
one neighbourhood: the seed, its parent, children, siblings and linked cards,
capped at ~org-sm-neural-size~.  Dismissed cards are walked *through* but not
shown -- the usual workflow extracts clozes and dismisses the source topic, so
that topic is the bridge between sibling clozes.  Grading works as an early
review; press ~s~ to read a card without touching its schedule.  This is the
answer to fragmentation: cards that are retrievable but never meet.

* Capture and card workbench

Both use one buffer type (~org-sm-capture-mode~) with one visual convention
and one commit command:

| In the buffer | Means                                                       |
|---------------+-------------------------------------------------------------|
| leading text  | one card's body (text before any ~**~ heading)              |
| each ~**~     | one more card                                               |
| ~C-c C-c~     | ~org-sm-capture-commit~: write back whichever are present    |
| ~C-c C-k~     | discard, touching nothing                                    |

** ~org-sm-capture~ (=M-z= / =C-c s c=)

Grabs the region (via ~M-w~, so pdf/nov/~reader-mode~ work too) or else the
clipboard into a side buffer, so you can see and edit it before writing.
Committing creates brand-new top-level topic cards, due tomorrow, in a single
inbox: an ~sm-cards~ heading in ~sm-cards.org~ under ~org-sm-directory~ (both
created on demand; change with ~org-sm-capture-file~ / ~org-sm-capture-olp~).
Refile into per-topic files yourself afterwards.

*No AI here.*  Capture stores exactly what you grabbed: at capture time you
don't yet know what the material is worth, the action must stay instant, and a
card you never revisit doesn't deserve tokens.

** ~org-sm-capture-clipboard-notify~

Saves the system clipboard immediately as one topic card in the same inbox,
then sends a desktop notification with the captured text.  Unlike
~org-sm-capture~, it does not open an editable buffer or require ~C-c C-c~;
use it for one-key popup/menu capture.

** ~org-sm-card-workbench~ (=C-c s A=)

Run it on the card you are reading.  The card's body is copied in as leading
text; nothing changes in the source until you commit.  Then ~C-c C-c~:

- the leading text replaces the card's body in place (type / schedule / id
  untouched);
- each ~**~ heading becomes a new scheduled *child* topic with a
  back-reference appended — existing children are left alone.

So one workbench covers a pure refine (no ~**~ headings), a pure split, or
both at once — by hand, or with the AI actions below.

* Extract

Select text, then ~org-sm-item-extract~:

- *topic* — the selection becomes the child body.
- *cloze* — the full parent body is copied to the child, selection wrapped as
  ~{{answer}}~.

The selection in the parent gains an ~[[id:...][title]]~ back-reference.

* Properties

| Property         | Type              | Description                     |
|------------------+-------------------+---------------------------------|
| ~SRS_TYPE~       | ~topic~ / ~cloze~ | Card type                       |
| ~SRS_LAST~       | ISO 8601          | Last review timestamp           |
| ~SRS_STATE~      | symbol            | FSRS state (cloze only)         |
| ~SRS_STABILITY~  | float             | FSRS stability (cloze only)     |
| ~SRS_DIFFICULTY~ | float             | FSRS difficulty (cloze only)    |
| ~SRS_STEP~       | int               | FSRS learning step (cloze only) |

~SCHEDULED~ is the due date for both types.

* AI assistant (org-sm-gptel)

Optional, powered by [[https://github.com/karthink/gptel][gptel]]:

#+begin_src elisp
(with-eval-after-load 'gptel (require 'org-sm-gptel))
#+end_src

One division of labour: *the AI points at text and rewrites prose on
request; deciding what becomes a card, and cloze deletion, stay with you.*
Generating the item is where encoding happens; an AI that writes your cards
leaves you recognising its sentences instead of recalling yours.

| Key       | Command                  | Acts on                         | Result                         |
|-----------+--------------------------+---------------------------------+--------------------------------|
| ~x~       | ~org-sm-gptel-suggest~   | the region, else the text on screen | up to 3 underlined passages |
| ~?~       | ~org-sm-gptel-explain~   | the region, else the paragraph at point | an explanation in the card's chat |
| ~C-c C-a~ | ~org-sm-gptel-card-ai~   | the body in a card workbench    | the body rewritten             |

*suggest* — the AI may only quote: each suggestion is a verbatim passage of
the source plus one line on why it is worth its own card.  Quotes are
located in the text (exactly, then ignoring re-wrapped whitespace); one that
cannot be found is dropped, so a suggestion never points at text that is not
there.  Suggestions are drawn as wavy underlines and nothing is written:
on an underline, ~RET~ extracts it through ~org-sm-extract~ -- the passage is
highlighted in place and the child sits where it came from, exactly as if you
had selected it -- ~DEL~ erases it and ~TAB~ moves to the next.  Underlines
vanish when the review moves on or the buffer is killed.  Scope is the
screen rather than the card, so a long article is read a screenful at a time
and each request stays short.

*explain* -- one chat per card, reused, so a second question about another
paragraph continues the conversation.  The message carries the passage, up
to ~org-sm-gptel-explain-context~ characters around it, and the source page
when the card has a ~page:~ link.  A half-written draft at the end of the
chat is never sent along: the new question waits until it is gone.

*card-ai* -- refine (clean prose, keep every causal link, flag
~【需补充】~ where a conclusion lacks its why), 简化 (cut to the core) or a
custom instruction.  Only the leading body text is rewritten; ~**~ cards
you typed below it are kept.  An async reply is discarded if you edited the
buffer meanwhile.  Prompts: ~org-sm-gptel-system-topic~ / ~-cloze~ /
~-simplify~ / ~-suggest~ / ~-explain~.

* Provenance: capturing from PDF, EPUB and web (org-sm-source)

Capture records where the text came from, so a card can be traced back years
later.  Nothing here calls AI.

- In a PDF (~emureader-mode~) or EPUB (~nov-mode~) buffer, ~M-z~ appends
  ~来源：[[page:/path/book.pdf::42][《book》p.42]]~ or a ~nov:file::doc:point~
  link, and files the card with the rest of that document's cards
  (=org-sm-source-target-file=: the file already linking the document, else the
  note whose ~#+reference:~ matches its name) instead of the shared inbox.
  Routing is buffer-local, so one book's extract never moves the next capture.
- PDF pages are images in emureader, so ~org-sm-capture-page~ reads the page for
  you: ~mutool draw -F txt~ for a text layer, then tesseract
  (~org-sm-source-ocr-languages~, default =chi_sim+eng=) for scans.  OCR takes
  seconds, so it runs in a background process and caches under
  ~org-sm-source-cache-directory~.
- ~C-c C-o~ on a ~page:~ link reopens the document at that page.
- The AI explanation (~?~) adds the page text behind the card's ~page:~ link to
  its opening message: the reasoning a card left behind is usually still on the
  page.

* Importing books and articles (org-sm-import)

Incremental reading needs the material inside the vault: only Org text carries
extraction highlights, read points and child cards in both Emacs and the web
reader.  ~org-sm-import-file~ (EPUB, HTML, Markdown, DOCX …) and
~org-sm-import-url~ (readability, then pandoc) write one note of topic cards:

- chapters become ~[T]~ cards at the shallowest heading level where most
  headings carry text, so a book with parts still splits by chapter;
- shallower headings stay as containers, deeper ones are flattened into ~§~
  lines (a card's body ends at its first child heading);
- chapters shorter than ~org-sm-import-min-chars~ stay as plain headings (title
  page, copyright);
- chapters come due in reading order, ~org-sm-import-topics-per-day~ per day;
- embedded images are extracted next to the note and linked relatively;
- import is idempotent: the note records ~#+source:~ and re-importing refuses.

Import does no AI and makes no clozes.  PDFs are not imported: their value is
layout, so they stay in emureader and contribute through
~org-sm-capture-page~.

* Zotero import (org-sm-zotero) — deprecated

Superseded by ~org-sm-source~ and ~org-sm-import~: read in Emacs, capture with
~M-z~, import EPUB chapters directly.  The module still works and is still
tested, but it is no longer loaded by default and its key is unbound.

Read-only client for Zotero 10's built-in Local HTTP API
(~http://127.0.0.1:23119/api~).  Reads go through Zotero's live process without
touching ~zotero.sqlite~ on disk; newly highlighted passages are visible
immediately and trashed items are excluded automatically.

- ~M-x org-sm-zotero-import~: pick books and import new PDF/EPUB highlights (and
  commented image/area annotations) as topic cards under ~sm-cards / <book>~,
  ordered by Zotero's reading ~sortIndex~.
- ~org-sm-zotero-color-rules~: maps highlight hex colors to actions (by default,
  red ~#ff6666~ / ~#ff0000~ stamps priority ~[#A]~, gray ~#aaaaaa~ is ~ignore~
  for pure reading marks, and other colors create standard topic cards).
- Deduplicates vault-wide by ~ZOTERO_KEY~; adding a comment later in Zotero to
  an already imported highlight appends ~批注：~ in place without resetting its
  schedule.
- Cards include a ~[[zotero://...][在 Zotero 中打开]]~ deep link (registered as
  an Org link type so ~C-c C-o~ jumps straight to the PDF/EPUB annotation in
  Zotero).

* Web review & mobile editing (org-sm-web)

Phone browser UI for reviewing and editing due cards over a local network; needs
[[https://github.com/skeeto/emacs-web-server][simple-httpd]].  It supports Anki-style review, one-click cloze reveal, rating,
topic rescheduling, and a native iOS-optimized editing sheet with text selection,
cloze creation (~{{...}}~), and child card extraction.

#+begin_src elisp
(require 'org-sm-web)
(org-sm-web-start) ; prints http://LAN-IP:8842/ for your phone
#+end_src

On startup the server listens on ~0.0.0.0~ and prints a URL such as
~http://192.168.31.17:8842/~.  Open it from a phone on the same *trusted*
LAN.  This default is not authenticated; do not expose the HTTP port to the
Internet.  For SSH-only access, set ~org-sm-web-bind~ to ~"127.0.0.1"~ before
starting, forward phone port 8842 over SSH to ~127.0.0.1:8842~, then open
~http://localhost:8842/~.  ~org-sm-web-token~ can add a ~?t=TOKEN~ check but
does not encrypt HTTP traffic.  If the displayed LAN URL is unreachable,
check the phone's Wi-Fi network and the host firewall.  The snapshot carries
a revision for each card; stale writes are rejected rather than silently
replacing concurrent edits or reviews.

Its core endpoints are:
- ~GET /api/session~: Preloads the entire due queue (~90KB JSON) in a single request.
- ~POST /api/review/:id~: Rates or reschedules a card (~rating=~ or ~action=~).
- ~POST /api/patch/:id~: Saves edits to card title and body.
- ~POST /api/extract/:id~: Extracts a selected text region into a new child card.
- ~GET /api/git/diff~: Shows notes status and tracked changes (staged and unstaged).
  Untracked file *names*, but not their contents, appear in the preview.
- ~POST /api/git/sync~: Pulls (only with saved notes buffers), or commits only
  paths under ~org-sm-directory~ and pushes.  These synchronous Git commands
  block Emacs until they finish; do not use this endpoint with untrusted repos.

Reading in the browser (long topics):

- ~POST /api/readpoint/:id~: moves the card's read-point anchor (~[[rp:ID][📖]]~)
  to a body offset; the snapshot ships ~:readpoint~ so a phone resumes where
  Emacs stopped.  Double-tap the body to move it, or use "记到屏幕顶部".
- ~POST /api/priority/:id~: sets ~cookie~ to ~A~, ~B~ or ~C~.
- ~GET /api/image?path=~: serves an image linked from a card body, restricted to
  ~org-sm-directory~ or ~org-sm-web-image-roots~ and to image extensions, so a
  crafted link cannot read anything else over the LAN.
- Extracted spans (~⌈…<T>~) render highlighted; the same text is highlighted in
  Emacs, because both views read one Org body.  Cards arrive already in
  ~org-sm-queue-order~; the client takes the head for a light session.
